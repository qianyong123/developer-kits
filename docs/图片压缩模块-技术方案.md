# 砺 · 图片压缩模块 — 技术方案

> 版本：v0.1（本期）  
> 日期：2026-08-06  
> 配套文档：[图片压缩模块-需求文档](./图片压缩模块-需求文档.md)、[公共技术方案](./公共技术方案.md)

## 1. 模块专属依赖

| 能力 | 选型 | 说明 |
| --- | --- | --- |
| 解码/编码 | Canvas API + `createImageBitmap` | 零依赖，覆盖 WebP/JPEG/PNG |
| 元数据（仅“保留”开启时） | piexifjs（读取 + 写入 JPEG） | 动态 import，按需加载 |

## 2. 压缩引擎抽象（可扩展）

定义统一的编码器接口，UI 只依赖接口，不依赖具体实现：

```ts
interface ImageEncoder {
  id: 'webp' | 'jpeg' | 'png';
  encode(source: ImageBitmap, options: EncodeOptions): Promise<Blob>;
  supportsQuality: boolean; // WebP/JPEG true，PNG false
  minQuality: number;
  maxQuality: number;
}
```

- WebP / JPEG / PNG 使用 Canvas `toBlob` 实现。
- 后续如需新增编码格式，只需注册对应的 `ImageEncoder`（如 WASM 编码器），UI 与二分搜索逻辑零改动；当前已决策不引入 AVIF。
- 编码器注册表 `getEncoder(format)` 统一获取实例。
- 输出格式支持 `original`（与输入一致）：按文件类型映射 JPEG / WebP / PNG，GIF / BMP 统一转 PNG 并提示；界面默认选项为“原格式”。

## 3. 解码与预处理

- 使用 `createImageBitmap(file)` 解码，失败时回退到 `<img>` + Canvas。
- 通过 `image-orientation: from-image` 或 EXIF 处理保证手机照片方向正确。
- 可选最大边长限制（默认 4096px）：超过则等比例缩小，避免超大图耗尽内存。
- 处理完成后调用 `bitmap.close()` 及时释放内存。
- “保留元数据”默认关闭（默认剥离，与 TinyPNG 网页版一致）：开启时用 piexifjs 读取原图 EXIF，编码后写回 JPEG；WebP / PNG 的元数据写回不支持，UI 上如实标注。

## 4. 两种压缩模式

### 4.1 手动质量模式

- 质量滑块变化 → 对每张图调用 `encoder.encode(bitmap, { quality })` → 更新结果与预览。
- 大图或数量多时做**防抖（300ms）**，避免滑块拖动时高频重压缩。
- PNG 始终有损量化：质量滑块映射为调色板颜色数（16–256 色）+ 预乘空间 Floyd–Steinberg 抖动。

### 4.2 目标体积模式（二分搜索）

- 对支持质量参数的格式，在 `[minQuality, maxQuality]` 区间二分，目标为“不超过目标体积的最大质量”。
- 迭代约 7 次即可收敛到 ±1% 质量精度；每次编码前检查 `size <= targetBytes * 1.05` 提前退出。
- 搜索失败（最低质量仍超目标）→ 标记“无法达标”，按用户策略处理。
- PNG：对“调色板颜色数”做二分搜索。
- 同一批次中，每张图独立搜索（不同图片对质量敏感度不同）。

## 5. PNG 有损量化

自研方案，零第三方依赖：

1. **建调色板**：4D 预乘 alpha 直方图（RGB 各 4bit + alpha 5bit）中位切分，每色自带 alpha，经 tRNS 输出，支持半透明渐变/光晕；退化切分自动换通道，条目 ≤256 满足 PLTE 上限。
2. **精修**：k-means 迭代（kd-tree 加速 4D 最近邻）。
3. **自适应颜色数**：仅目标体积模式启用。
4. **抖动**：自适应 Floyd–Steinberg（预乘空间 4 通道误差扩散，边缘/全透明区域不扩散）。
5. **编码**：每行自适应 filter（None/Sub/Up/Avg/Paeth）→ 索引色 PNG（PLTE / tRNS / IDAT，zlib 压缩）。

质量值映射为颜色数 16–256。

## 6. 批量队列与并发控制

- 手写轻量信号量（`runPool`），默认并发 2，可配置。
- 任务状态机：`pending → processing → done | error`。
- 全局参数变更 → 重新入队，已完成的图片标记为“过期结果”而非直接丢弃。
- 支持取消：用户可中断整个队列，已完成的保留。

## 7. 对比预览

- 原图与压缩图使用对象 URL 保存，并排展示体积与压缩率。
- 滑动对比（拖拽分割线）用于细节比较，缩放使用 `object-fit: contain` 容器。
- 预览 Blob 用 `URL.createObjectURL` 生成，组件卸载时释放。

## 8. 性能与内存策略

- 解码后的 `ImageBitmap` 用完即 `close()`。
- 批量处理采用“一次只保留少量原图解码结果”的流水线，避免同时驻留所有大图。
- 预览缩略图单独生成小尺寸版本，不直接复用全尺寸压缩结果。
- 处理逻辑全部 `async`，UI 线程不被长任务阻塞；必要时用 `requestIdleCallback` 分摊非紧急工作。
- 若内存占用过高（页面卡顿/崩溃风险），记录并提示用户分批处理。

## 9. 浏览器兼容性

| 能力 | 最低支持 | 说明 |
| --- | --- | --- |
| `canvas.toBlob('image/webp')` | Chrome 50 / Safari 16+ 等 | 主路径 |
| `createImageBitmap` | 现代浏览器 | 有降级方案 |

- Safari 16 以下 WebP 编码不可用 → 自动降级提示改用 JPEG。
- 以桌面 Chrome / Edge 与移动端 Safari / Chrome 为主要目标，Firefox 做兼容性验证。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 超大图/大量图片导致内存暴涨 | 浏览器崩溃 | 最大边长限制、并发控制、流水线释放 |
| 已压缩过的图片无法达到目标体积 / 重编码后变大 | 用户困惑 | 明确提示“无法达标”；压缩后大于原图时自动保留原图 |
| PNG 有损量化有轻微画质损失 | 保真敏感场景不满 | 量化结果可对比预览；对保真有硬性需求建议转 WebP/JPEG |
| Safari WebP 编码缺失 | 功能不可用 | 自动降级 + 提示 |
| 目标体积模式耗时（每张多次编码） | 批量慢 | 并发 + 二分提前退出 + 进度反馈 |
| WebP 元数据写回能力有限 | “保留元数据”效果不一致 | UI 标注支持范围（仅 JPEG），避免误导 |
